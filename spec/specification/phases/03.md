# Phase 03 — System architecture and service boundaries

**Owner role**  Platform architect  
**Documentation status**  Drafted and structurally checked  
**Engineering status**  Proposed, with runtime evidence pending

## Purpose and scope

Separate UI, control plane API, durable store/outbox, orchestration worker, untrusted build runner and host agent. Single-host deployment is a topology candidate. Logical boundaries remain even if API and worker share a binary. API owns authorization and desired state. Worker owns operation scheduling. Agent owns scoped host observation and effects. External providers enter through adapters. No browser route to the helper or datastore.

## Contract and operational behavior

Deployment candidate from the PRDs is an unprivileged Go modular monolith, static SvelteKit UI, SQLite WAL, systemd and a socket-activated helper. DEC-001 and DEC-002 govern adoption. Use same-origin UI-to-API communication. The orchestration boundary consumes durable operation intents. Host effects cross a typed helper boundary. Repositories and build processes run under separate principals, with no access to the management store or helper. An outage of a module or provider degrades that capability while preserving management access.

## Acceptance and test design

**REQ-P03-01 / AC-P03-01**. A mutation commits desired generation, operation and outbox event once before returning its operation ID. A worker restart cannot lose accepted work. Observed state is recorded independently and compared against desired state.

**TC-P03-01 · Procedure**. Kill API after commit and before response, retry with the same key, then restart worker after it reads the event.

**Expected**. One resource generation and one operation persist. Recovery starts or reconciles that operation.

**TC-P03-02 · Companion test**. Submit one authorized mutation and drain the outbox into the worker.

**Expected**. One desired generation and one operation are visible with a verified terminal observation.
