# Phase 11 — Runtime, process and service management

**Owner role**  Runtime lead  
**Documentation status**  Drafted and structurally checked  
**Engineering status**  Proposed, with runtime evidence pending

## Purpose and scope

Use capability-probed runtime adapters for PHP/FPM, Node, Python and supported binaries, with optional OCI gated separately. Scope each runtime environment, supervisor unit, service account, port and logs to its owner. Allowlisted service restarts obey protected-unit policy. Register version, limits, health and config generation. Reserve resources before start. All runtime-specific toolchains are untrusted in build contexts.

## Contract and operational behavior

Adapter manifest describes runtime family/version, packages, supervisor profile, resource limits and supported operations. Runtime instance holds owner, unit ID, workload identity, config generation, port reservations and secret refs. Validate and test config before restart. Inspect process identity before sending signals to handle PID reuse. Never expose arbitrary OS command launch through a runtime control. Terminal and OCI are disabled unless the scope and isolation gates are satisfied.

## Acceptance and test design

**REQ-P11-01 / AC-P11-01**. A request can start or restart only the mapped unit owned by the resource and only on an eligible host. On failed health, retain or restore the prior eligible service generation.

**TC-P11-01 · Procedure**. Restart a protected unit via an alias and start a tenant runtime that fails its health probe.

**Expected**. Protected unit unchanged. Failed runtime is degraded with resource lease released or old generation restored.

**TC-P11-02 · Companion test**. Configure supported per-site runtime and inspect supervisor identity and limits.

**Expected**. Mapped workload starts as scoped principal and health is observed.
