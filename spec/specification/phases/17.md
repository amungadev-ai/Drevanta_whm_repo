# Phase 17 — Identity, MFA, sessions and recovery

**Owner role**  Identity lead  
**Documentation status**  Drafted and structurally checked  
**Engineering status**  Proposed, with runtime evidence pending

## Purpose and scope

Separate password verification, MFA challenge and session issuance. Challenge and recovery tokens are purpose-bound, expiring and single-use. Reset revokes existing sessions, preserves MFA enrollment and requires fresh sign-in. Define server owner recovery through authorized local console or SSH with audited recovery grant and MFA-preserving policy. Bind recovery codes to one consumption, rotate on regeneration, and protect credentials at rest.

## Contract and operational behavior

Reset links bind account, purpose, expiry and unique token digest. Rotate session at authentication and privilege changes. Refresh/revocation obey policy revision. Keep MFA setup pending until proof, issue recovery codes once and store only verifier material. Server recovery additionally needs installation-local authority, narrow grant, observable audit, bounded lifetime and reviewed proof. Browser flows cover login, verify, both recovery options, reset and return to fresh login.

## Acceptance and test design

**REQ-P17-01 / AC-P17-01**. No authenticated workspace session before required MFA completes. Parallel reset and recovery-code submissions have one success each. Revoked sessions cannot perform another authorized request.

**TC-P17-01 · Procedure**. Replay an OTP/used recovery code, race a password reset token, and access an old session after reset.

**Expected**. Only the first valid use succeeds. Old sessions rejected. Enrollment remains and next sign-in requires MFA.

**TC-P17-02 · Companion test**. Sign in using enrolled MFA, reset password and sign in with the new password and MFA.

**Expected**. New session succeeds only after fresh MFA; old session remains revoked.
